# Cashbook 隐私与数据安全架构

## 1. 威胁模型

Cashbook 是个人/家庭自用记账应用，但仍按高敏感金融数据应用设计。

重点防范：

- 应用读取超出记账所需的通知、短信或屏幕内容。
- 原始通知、短信、截图被日志、崩溃报告或第三方 SDK 意外上传。
- 第三方 AI 服务获得完整支付通知或短信原文。
- 共享服务器泄露完整交易明细或认证凭据。
- 多种采集渠道对同一笔交易重复入账。

## 2. 数据分级

### S0：禁止离开设备

默认不得上传或长期保存：

- 完整通知原文
- 完整短信原文
- 原始支付截图
- OCR 完整原文
- 验证码
- 聊天消息正文
- 身份证号、银行卡完整卡号
- 支付密码、登录密码等认证秘密

### S1：可进入结构化账本

仅在用户需要时保存：

- 金额
- 收入/支出方向
- 商户或交易对象的必要名称
- 时间
- 支付渠道
- 账本归属
- 创建者
- 分类
- 交易号的脱敏/哈希形式（如需去重）
- 解析置信度

## 3. 采集权限分级

### A. NotificationListenerService：允许，默认主通道

系统授权本身较宽，因此代码必须在回调入口立即执行包名白名单过滤。

默认白名单只包含用户显式开启的金融来源，例如：

- 微信
- 支付宝
- 指定银行 App

处理要求：

1. 非白名单通知立即丢弃。
2. 白名单通知只在内存中解析。
3. 不把原文写入数据库。
4. release 构建禁止输出原文日志。
5. 只生成 S1 结构化 CandidateTransaction。
6. 默认不把原文发送给云端 AI。

### B. 用户主动截图/OCR：允许，次级通道

优先采用“用户主动分享/选择截图给 Cashbook”的方式。

默认：

- OCR 尽可能本地完成。
- 完成结构化提取后删除临时图。
- 原图不上传共享服务。
- 自动监听整个图库不是第一优先级。

### C. SMS：默认关闭

短信权限能够暴露验证码、银行通知、私人通信等高敏感内容。

V0.1 不申请 READ_SMS/RECEIVE_SMS。

如果以后确认银行卡交易必须依赖短信：

- 做成独立可选模块。
- 用户显式开启。
- 首先按发送方白名单过滤银行短信。
- 原文不落盘。
- 验证码字段主动擦除。
- 禁止上传完整短信到云端。

### D. AccessibilityService：默认关闭/实验性

无障碍服务可能读取当前窗口节点树，权限面明显大于记账需求。

只有当特定支付场景无法通过通知、截图或账单导入覆盖时才考虑。

若启用：

- packageNames 强制限定微信/支付宝等目标包。
- 只监听必要的窗口事件。
- 不读取其他 App。
- 不执行自动点击、输入等无关操作。
- 不保存完整页面文本。
- 只生成结构化候选交易。

### E. MediaProjection/连续屏幕捕获：不作为默认方案

后台连续截屏隐私面过大，并且现代 Android 对屏幕捕获具有明确的会话授权约束。

Cashbook 默认不实现常驻屏幕录制式采集。

### F. 隐私诊断：默认关闭，仅记录元数据

为了在不同 Android ROM、微信/支付宝版本上定位漏识别问题，允许用户主动开启本地诊断。

允许记录：

- 来源：仅微信 / 支付宝
- Android notification category
- Android notification channelId
- 处理结果：消息类拦截 / 未生成候选 / 已生成候选
- 时间

明确禁止记录：

- 通知标题
- 通知正文
- bigText
- 金额
- 商户
- 订单号
- 聊天内容
- Notification.extras 原始内容

诊断规则：

1. 默认关闭。
2. 非微信/支付宝通知连元数据也不记录。
3. 最多保留 50 条。
4. 最长保留 24 小时。
5. 只保存在手机本地，不同步云端。
6. 用户可随时清空。
7. “复制诊断”只复制上述元数据字段。

## 4. 候选交易层

任何自动采集渠道都不能直接写正式交易。

统一转换为：

```
CandidateTransaction
- source
- amount
- direction
- merchant
- timestamp
- payer
- confidence
- fingerprint
```

处理流程：

```
Raw Event
  -> Source Adapter
  -> Local Parser
  -> CandidateTransaction
  -> Deduplication
  -> Confidence
  -> Auto Confirm / Manual Confirm
  -> Transaction
```

这样可防止通知、OCR、无障碍同时抓到一笔消费时重复入账。

## 5. 网络边界

默认只允许以下数据进入自托管共享服务：

- 正式结构化交易
- 账本、分类、预算
- 共享成员与必要账户资料

不得上传：

- 原始通知
- 原始短信
- 原始截图
- 全量 OCR 文本

如以后增加 AI：

1. 优先本地模型或规则。
2. 外部模型默认只接收脱敏、裁剪后的最小文本。
3. 外部 AI 功能必须有独立开关。
4. AI 不参与密码、验证码、身份认证信息处理。

## 6. 日志规范

release 构建禁止输出：

- notification.text
- SMS body
- OCR raw text
- token
- password
- Cookie
- Authorization header
- 完整银行卡号

允许日志：

- source=wechat
- parse_success=true
- amount_detected=true
- confidence=0.93
- dedup_hit=false

金额是否写日志默认也应关闭。

## 7. V0.1 权限预算

V0.1 目标权限：

- INTERNET：共享账本同步
- POST_NOTIFICATIONS：Cashbook 自身提示
- Notification access：用户手工开启，用于支付通知

V0.1 默认不申请：

- READ_SMS
- RECEIVE_SMS
- Accessibility
- MediaProjection 常驻捕获
- 联系人
- 位置
- 麦克风
- 相机（除非后续主动拍照 OCR）
- 全量媒体库读取

## 8. 设计原则

任何新权限进入项目之前，需要回答三个问题：

1. 没有这个权限，核心记账闭环是否真的无法工作？
2. 能否使用更窄的权限或用户主动操作替代？
3. 获取的数据能否在设备内立即裁剪成结构化字段并销毁原文？

只要答案允许，就选择更窄的方案。
